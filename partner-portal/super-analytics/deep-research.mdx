<Warning>
  **Deep Research runs outside the main application by default.** Reports are queued to the platform manager service (the background worker service). If the platform manager service is not configured or is unreachable, up to 2 reports can run in-process concurrently before overflow requests are queued for when it recovers. This is intentional — it protects the platform from being slowed down by research workloads during outages.
</Warning>

## What Deep Research does

The **Deep Research** tab lets you commission an AI research report on any subject. You give it a subject (a customer name, a company URL, a domain) and a brief scope, and it returns a structured report covering:

- What the subject does / who they are
- Key signals from their public web presence (website, social profiles, news mentions)
- Relevance to your business (account expansion opportunity, churn signal, competitive intelligence)
- Recommended next steps

Reports are saved as `ResearchRun` records — you can re-open them later, compare runs over time, and share the link with a teammate.

## Starting a research run

1. Open **Super Analytics → Deep Research**.
2. In the **Subject** field, enter what you want researched. This can be:
   - A company name (e.g. "Acme Corp")
   - A website URL (e.g. `acme.com`)
   - A customer name from your portal
3. Optionally add a **focus** (e.g. "expansion opportunity", "churn risk", "competitive positioning").
4. Click **Run**. The research is queued and you'll see a status indicator.
5. When the report is ready (usually 1–5 minutes), it appears in the **Runs** list. Click it to read.

## What the pipeline does

Behind the scenes, Deep Research runs a multi-step pipeline:

| Step | What happens |
|------|-------------|
| Web search | Searches the public web for the subject |
| Website scrape | Fetches and reads the subject's main website (safely — no internal-network access) |
| Social discovery | Finds public social profiles linked to the domain |
| SEO snapshot | Reads public SEO signals (page count, technical health) |
| Places lookup | Looks up business information from public directories |
| Synthesis | Combines all findings into a structured narrative report |

<Note>
  The pipeline only accesses public information. It does not make requests to internal IP ranges, cloud metadata endpoints, or private network addresses. SSRF (server-side request forgery) protections pin DNS lookups to validated addresses before making any HTTP requests.
</Note>

## Research run statuses

| Status | Meaning |
|--------|---------|
| `queued` | Waiting for a worker slot |
| `running` | The pipeline is actively fetching and analysing |
| `completed` | Report is ready to read |
| `scheduled` | Queued for the platform manager service to pick up (shown when in-process capacity is full) |
| `failed` | The pipeline encountered an unrecoverable error. Retry from the run detail page. |

---

## Background worker and in-process fallback

Deep Research is designed to run on the platform manager service — the platform's background worker service. If the manager service is configured and reachable, all research runs go there and the main application stays free.

When the manager service is not available (not configured, or temporarily unreachable):

- The main application will run up to `SUPER_ANALYTICS_INPROCESS_MAX` (default: 2) research pipelines concurrently in-process.
- Any research request beyond that limit is set to `scheduled` status and will be picked up when the manager service recovers or a scheduled check runs.

This means a manager service outage degrades research capacity (interactive runs may queue) but does not affect voice agents, billing, or other features.
