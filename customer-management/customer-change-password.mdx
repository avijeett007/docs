## Overview

Customers on your whitelabel portal set and change their passwords through a single **Change Password** page. The rules for which fields appear and what is verified depend on how the customer arrived at the page.

---

## First login

When a customer logs in for the first time using the temporary password from their welcome email, they are redirected to the Change Password page to set a permanent password.

> 📷 **Screenshot needed:** _Add a screenshot of the Change Password page in first-login mode, showing the "Current Password" field with the "The temporary password you just signed in with" hint text, and the New Password / Confirm Password fields._

**What the customer sees:**

- **Current Password** field, with a hint: _"The temporary password you just signed in with"_
- **New Password** field
- **Confirm New Password** field
- A **Set Password** button

The customer must enter the temporary password from their welcome email in **Current Password**. This confirms they have access to the original credentials before a new password is set.

<Note>
This behavior changed in a recent update. Previously, the first-login page skipped the Current Password field. Now it always requires it, which prevents an attacker who steals a session cookie from locking the legitimate customer out.
</Note>

---

## Magic-link password reset

When a customer uses the **Forgot password?** link, they receive a password-reset email with a one-time magic link. Clicking the link opens the Change Password page in reset mode — the link's authenticity is verified by the session token, so the customer does not need their old password.

> 📷 **Screenshot needed:** _Add a screenshot of the Change Password page in magic-link reset mode — showing only the New Password and Confirm New Password fields, with no Current Password field._

**What the customer sees:**

- **New Password** field
- **Confirm New Password** field
- A **Set Password** button (no Current Password field)

Once the password is set, the magic-link session is replaced with a regular session — the customer lands on their dashboard without needing to log in again.

---

## Voluntary password change

A customer who is already logged in and wants to change their password navigates to **Settings → Change Password** (or equivalent in your portal's nav).

**What the customer sees:**

- **Current Password** field
- **New Password** field
- **Confirm New Password** field
- A **Change Password** button

The current password is always required for a voluntary change.

---

## Partner impersonation

When a partner is previewing a customer's portal through the **Impersonate** feature, the Change Password page is visible but the form is blocked — submitting it returns a 403 error. This prevents an impersonating session from locking the customer out of their account.

<Warning>
If a customer contacts you saying they cannot change their password while you are impersonating their session, log out of the impersonation session first. The customer can then change their password normally.
</Warning>

---

## Summary of rules

| Scenario | Current Password required | New-password-only flow |
|---|---|---|
| First login (temporary password) | Yes — the temporary password | No |
| Magic-link password reset | No | Yes |
| Voluntary change | Yes — the existing password | No |
| Partner impersonation active | Blocked entirely | — |

---

## Password requirements

- Minimum 8 characters
- No maximum (standard bcrypt truncation at 72 bytes applies internally)
