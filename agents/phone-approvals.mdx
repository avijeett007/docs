## Overview

Phone Approvals let you mark specific tools as **high-risk**. When a customer's AI agent tries to call one of those tools — whether that agent is a Knova voice agent, a Claude or Codex session, an n8n workflow, or any other caller that uses a customer's MCP gateway — the call is **not executed until someone approves it on a paired phone**.

- **Customer controls:** the customer pairs one or more phones via their portal, then chooses approval-on per app or per tool.
- **Agency controls:** as a partner, you can set a default approval policy and lock rules that customers cannot override.
- **Off by default.** While `APPROVALS_ENABLED` is not turned on for your deployment, every tool call behaves exactly as it does today.

## How it works

1. **Agent calls a gated tool.** The MCP gateway checks whether this customer has an approval rule for the tool. If approval is required, the gateway immediately sends a push notification to the customer's paired phone(s).
2. **Code appears in the agent response.** The agent (or automation) receives `APPROVAL_REQUIRED` together with a 4-digit code. The same code appears on the phone notification.
3. **Customer approves on their phone.** Using Face ID or a fingerprint, the customer approves the action. The approval server records the decision.
4. **Agent calls the tool again.** When the agent (following the instructions returned with `APPROVAL_REQUIRED`) calls the **same tool with the same arguments**, the gateway claims the approval and runs the call immediately.
5. **Result returns normally.** The tool result flows back to the agent exactly as if no approval step existed.

### What the agent sees

| Situation | Agent receives |
|---|---|
| First call — no prior approval | `APPROVAL_REQUIRED` + 4-digit code + instructions to retry |
| Retry — approval is still pending | `APPROVAL_REQUIRED` + same code (no second push) |
| Retry — customer approved | Tool result (call runs now) |
| Retry — customer denied | `APPROVAL_DENIED` |
| Retry — arguments changed | A new approval request is raised |

Approvals are **single-use and argument-locked**. If the agent sends different parameters, a new approval request is created. This ensures the customer approves exactly the action shown on their phone.

## Setting up approvals (partner)

<Steps>
  <Step title="Enable the approvals feature">
    Go to **Settings → Approval Defaults** and click **Provision Approval Tenant**. Knotie will register your account on the approval server and store the credentials. This step requires `APPROVALS_ENABLED` to be turned on for your deployment.
  </Step>
  <Step title="Set default rules (optional)">
    On the same page, you can define default rules that apply to all new customers. You can also lock specific rules so customers cannot turn them off.
  </Step>
  <Step title="Customer pairs a phone">
    The customer logs into their portal and navigates to **Integrations → Approvals**. They click **Pair a phone** and scan the QR code with the Knotie phone app (available on iOS and Android).
  </Step>
  <Step title="Customer enables approvals per tool">
    The customer can toggle approval-on for an entire app (e.g., Gmail) or for individual tools (e.g., `gmail_send_email`). Tools that are considered high-risk are pre-marked in the portal.
  </Step>
</Steps>

## Customer portal: pairing a phone

1. In the customer portal, go to **Integrations → Approvals**.
2. Click **Pair a phone**.
3. Scan the QR code with the Knotie phone app. The device appears in the **Paired devices** list within a few seconds.
4. Paired devices can be renamed or revoked at any time from the same list.

## Customer portal: managing approval rules

The **Rules** tab shows all available tools grouped by connected app. For each tool you can:
- **Require approval** — the phone is asked every time this tool is called.
- **Allow freely** — the tool runs without interruption.

If your partner has locked a rule, you will see a lock icon and cannot change that setting.

## Security notes

- Approval decisions are signed with HMAC. A decision for one customer's tool cannot release a different customer's pending call.
- Approvals are single-use. Once claimed, the same approval cannot trigger a second call.
- Arguments are hashed. If the agent changes any argument, a new approval request is raised.
- Credentials are stored encrypted at rest (AES-256-GCM). The plaintext approval-server key is never logged.
- **Fail-closed:** if the approval server is unreachable, gated tool calls are refused, not run.

Any caller that reaches a customer's MCP gateway supports approvals:

| Caller | Notes |
|---|---|

| n8n automations | Via the Knotie n8n node |

## FAQ

**What if I don't have the phone app yet?**
The Knotie phone app is available via TestFlight (iOS) and will be on the App Store and Google Play when generally available. Contact support for access.

**What happens if no phone is paired?**
If approval is required but no device is paired, the tool call is refused with `APPROVAL_REQUIRED`. The agent receives instructions to have the customer pair a device first. Partner-locked rules that require a phone and have no device paired are shown as a warning in **Settings → Approval Defaults**.

**Does the customer have to approve every single call?**
Yes, per call. Approvals are single-use. If you want an automation to run a tool repeatedly without interruptions, do not mark that tool as requiring approval.

**Can the same approval code be used twice?**
No. The approval server marks each decision as consumed the moment it is claimed.
