## What the Knova agent is

The **Knova AI Receptionist** is Knotie AI's built-in voice agent. Unlike provider-imported agents (Retell, VAPI, Ultravox), Knova is deployed and managed entirely by the platform — you don't need a third-party agent account.

Knova answers inbound phone calls, fetches business context from your knowledge base, uses configurable tools (email, SMS, calendar), and routes or transfers callers as needed.

Key capabilities:

- **Inbound voice calls** over SIP via LiveKit Cloud
- **Dynamic system prompt** generated from your business profile
- **4 built-in tools**: Email, Knowledge Base, SMS, DateTime
- **Call transfer** — native SIP REFER with carrier-level caller-ID preservation
- **LLM fallback chain**: Cerebras → Gemini → GPT-4.1-mini → LiveKit Inference
- **STT fallback chain**: Deepgram → AssemblyAI → Groq Whisper → Cartesia → LiveKit Inference
- **Credit circuit breaker**: if a customer's credits hit zero, the number is automatically moved back to webhook routing so no LiveKit SIP minutes burn

## How call routing works

Knova uses a **SIP trunk routing** architecture. This is the new default for every phone number provisioned through auto-deploy or manual provisioning.

```
PSTN caller
    │
    ▼
Partner's Twilio account
    │  (Elastic SIP Trunk — one trunk per phone number)
    ▼
LiveKit Cloud shared Inbound SIP Trunk
    │  (one platform-wide trunk + dispatch rule)
    ▼
Knova agent worker
    │
    ▼
Conversation + tools
```

Each phone number gets its own Twilio Elastic SIP Trunk. All trunks point to a single LiveKit Inbound Trunk that dispatches calls to whichever Knova worker is available.

### Routing mode field

Every `PhoneNumber` record has a `routingMode` field:

| Value | Meaning |
|---|---|
| `sip_trunk` | Call goes via Twilio Elastic SIP Trunk → LiveKit (default for new numbers) |
| `webhook` | Legacy Twilio Programmable Voice → Connect Hub TwiML (fallback / older numbers) |

The platform automatically flips a number to `webhook` when a customer's credits reach zero, and can flip it back when credits are restored.

## Call transfer

When a caller asks to speak to a human, Knova initiates a **native SIP REFER** through the Twilio Elastic SIP Trunk. The trunk's `TransferMode=enable-all` setting propagates the REFER to the carrier, which preserves the original caller's number on the human's phone.

> **Note:** The human's phone will show the partner's Twilio number as the caller ID, not the customer's number. This is a carrier constraint — Twilio only allows a `callerId` that your Twilio account owns or has verified.

For phone numbers still on `webhook` routing, a conference-based fallback is used: the customer is placed in a Twilio `<Conference>` while a second outbound call dials the human.

## Prerequisites

Before enabling Knova for production:

1. **LiveKit Cloud project** — you need both the WSS URL and the SIP address for your project.
2. **Twilio account** — the partner's own Twilio account is used for purchasing and managing phone numbers.
3. **Run the one-time infrastructure setup** (see below).
4. **Database migration** applied to both the main app schema and `Knotie_Connect_Hub` schema.

## One-time infrastructure setup

### 1. Apply the schema migration

Run in **both** the main app and Connect Hub:

```bash
# Main app
npx prisma migrate dev --name sip_trunk_v2
npx prisma generate

# Connect Hub
cd Knotie_Connect_Hub
npx prisma migrate dev --name sip_trunk_v2
npx prisma generate

# KnotieManager (regenerate client only — uses main app schema)
cd KnotieManager
npx prisma generate
```

New columns added to `phone_numbers`:

| Column | Type | Default | Description |
|---|---|---|---|
| `routing_mode` | `String` | `"webhook"` | `"sip_trunk"` or `"webhook"` |
| `twilio_trunk_sid` | `String?` | `null` | Twilio Elastic SIP Trunk SID for this number |
| `routing_mode_changed_at` | `DateTime?` | `null` | When routing mode last changed |
| `routing_mode_changed_reason` | `String?` | `null` | Audit trail: `"provisioned"`, `"credits_zero"`, `"manual_enable"`, etc. |

### 2. Create the shared LiveKit infrastructure

Run once after applying the migration:

```bash
cd KnotieManager
npx ts-node scripts/setup-shared-livekit-sip.ts
```

The script creates:

1. **Platform-wide Inbound SIP Trunk** — accepts SIP traffic for all Knova numbers
2. **Dispatch Rule** — routes inbound calls to the Knova agent worker

The script outputs two IDs:

```
LIVEKIT_SHARED_SIP_INBOUND_TRUNK_ID=ST_xxxxxxxxxxxx
LIVEKIT_SHARED_SIP_DISPATCH_RULE_ID=SDR_xxxxxxxxxxxx
```

Copy these values into the `.env` files for KnotieManager, Connect Hub, and the knova-agent service.

> **Default security mode**: the trunk is created without SIP auth — the `numbers` allowlist on the trunk controls access. For mutual-auth setup, set `ENABLE_LK_SIP_AUTH=true` before running the script.

## Running the Knova agent worker

The Knova agent is a Python LiveKit Agents worker. In production, deploy it via Docker:

```bash
cd documentations/livekit_agent_examples
docker compose -f docker-compose.knova.yaml up -d
```

Verify it registered:

```
✅ "registered worker", "agent_name": "AI_Receptionist_Knova"
```

For local development and testing without Connect Hub, the agent falls back to `agent-config.json`.

## Credit circuit breaker

The Knova agent calls Connect Hub's `/agent-inbound-validate` endpoint at the start of every call. If a customer's credit balance is zero:

1. The endpoint returns `deny`.
2. The agent does not engage the LLM — no LiveKit SIP minutes are consumed.
3. KnotieManager flips the phone number's `routingMode` to `webhook` and restores the Twilio `VoiceUrl` to the legacy Connect Hub endpoint.
4. Future calls for that number go through the webhook path instead.

When the customer tops up credits, the number can be re-enabled for SIP trunk routing manually or via a re-provisioning flow.

The endpoint is **fail-open**: if Connect Hub is unreachable, the agent proceeds normally so calls are not dropped during a Connect Hub outage.

## Auto-deploy integration

When a prospect completes the 9-step SaaS onboarding flow, the platform's auto-deploy runner:

1. Purchases a phone number via `PhoneProvisioningService`
2. Creates a Knova agent record via `KnovaAgentService` (builds system prompt from business profile, configures tools)
3. Maps the number to the agent via `PhoneAgentMappingService`
4. Creates the Twilio Elastic SIP Trunk for that number
5. Adds the number to the shared LiveKit Inbound Trunk

New numbers default to `sip_trunk` routing.

See [Auto-deploy](/partner-portal/auto-deploy) for prerequisites and credit requirements.

## Troubleshooting

- **Agent worker not registering**
  - Confirm `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` are correct.
  - Check that `KNOVA_AGENT_NAME` matches what the dispatch rule routes to (default: `AI_Receptionist_Knova`).
- **Calls go to voicemail / not reaching the agent**
  - Verify `LIVEKIT_SHARED_SIP_INBOUND_TRUNK_ID` is the same on all three services.
  - Check the phone number's `routingMode` — if it's `webhook`, it won't reach the Knova worker.
  - Confirm the Twilio Elastic SIP Trunk's origination URI points to `KNOVA_SIP_ADDRESS`.
- **Call transfer fails**
  - The Twilio Elastic SIP Trunk must have `TransferMode=enable-all`.
  - Only numbers provisioned via the SIP trunk path support native REFER. Numbers on `webhook` routing use conference transfer.
- **`LIVEKIT_SHARED_SIP_INBOUND_TRUNK_ID` is empty**
  - The one-time setup script hasn't been run, or its output wasn't saved. Re-run `setup-shared-livekit-sip.ts` and copy both IDs.
